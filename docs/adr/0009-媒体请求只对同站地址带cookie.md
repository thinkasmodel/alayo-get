# ADR-0009：媒体请求只对同站地址带 cookie

- **状态**：已采纳
- **日期**：2026-10-08（ALAG-18，安全审计 S4，用户决定）

## 决策

媒体剪藏的探测与下载请求，只在**媒体地址与被保存页面同站**时带 cookie（`credentials: 'include'`）；跨站一律不带（`'omit'`），但照常下载。同站按 schemeful site 判：协议相同，且按 Public Suffix List 算出的 eTLD+1 相同（私有后缀如 `github.io` 也算后缀）。带 cookie 的请求若跟随重定向落到跨站目标，响应被丢弃并提示用户。这项重定向检查只比站点、不比协议：同站页面上的 http 媒体地址 301 到同主机的 https 很常见，协议升级不改变请求落在哪个站点，按 schemeful 判会误拒；是否带 cookie 的初始判定仍按 schemeful site。

两处有意的例外：
- 正文图片下载一直不带 cookie（原有行为）。
- YouTube / B 站视频页抓取带 cookie：目标被代码限定为这两个站点，请求是只读的页面 GET，且右键保存链接时被点的链接与宿主页面几乎总是跨站，套同站规则会让它永远不带 cookie。

## 理由

- 扩展持有 `<all_urls>`，对有 host permission 的目标会附带 SameSite=Strict cookie；普通网页的 `<img>` 请求做不到这一点。攻击者页面指定一个指向用户已登录站点的媒体地址，用户保存时就会借扩展权限发出带登录态的 GET/HEAD。
- 「一律不带」会让站内登录后才能下的 PDF/附件存不下来；同站规则覆盖这个合法场景，又挡住页面指定跨站地址这条路。
- 重定向发生在请求发出之后，cookie 已经送出，只能在响应侧止损。

## 后果

- 跨站且需要登录的文件存不下来，用户会看到说明「文件在另一站点、可能需要登录、扩展不把登录态发给别的站点」。以后若有需要，可以加一个失败后「用登录身份重试」的显式确认入口，那是用户对这个具体地址的一次授权。
- 运行时依赖多一个 `tldts`（MIT，Public Suffix List）。
- `docs/store/permissions.md` 的 host permission 说明随之补一句。

## 考虑过的方案

- **一律不带 cookie**：最安全，但砍掉登录态附件这个用例。
- **先不带、失败后自动带 cookie 重试**：攻击者的地址跳转到目标站时，第一次无 cookie 请求收到 401 会触发带 cookie 的重试，挡不住。
- **`redirect: 'manual'`**：扩展里拿到的是 opaqueredirect，读不到 Location，无法自己判断目标再决定。
