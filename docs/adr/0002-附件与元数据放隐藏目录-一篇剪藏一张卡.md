# ADR-0002：附件和元数据侧档放进隐藏目录，一个剪藏对应 Workbench 一张卡

- **状态**：已采纳
- **日期**：2026-10-06

## 决策

剪藏库根目录下平铺所有可见的剪藏。文章剪藏、书签剪藏、流媒体剪藏引用的图片和封面，放在 `.assets/<id>/` 里，Markdown 用相对路径引用。媒体剪藏的出处等元数据，放在 `.meta/<id>.json` 里。

## 理由

Workbench 发现新文件时，只要文件路径在监控根以下有任何一级以 `.` 开头，就不会报告它（31.1 `app/Sources/FileboardKit/Domain/DiscoveryExclusion.swift:59`，NKS-632）。所以点开头目录里的附件不会在"待纳入"里一张张冒出来，一篇带十张图的文章在画布上只有一张卡。不这样放的话，每张图都会被报成一个新文件，各自成卡。

## 考虑过的方案

- **每篇文章一个目录**：md 和图片放在同一个目录里，在 Workbench 里会变成"一组卡"，图片和正文被拆开。
- **让 Workbench 识别"文章包"目录**：语义上最干净，但需要改 Workbench。

## 后果

- 在 Finder 里默认看不到附件。md 文件本体一旦被移出剪藏库，图片引用就会断，以后用导出功能或附件跟随移动来解决。会移动文件本体的操作有：在 Finder 里拖走；Workbench 里给组设了去向后执行移动（ApplyEngine 实层操作，需要用户显式发起）。Workbench 的"归位"只调整卡片在画布上的位置，不动文件本体（31.1 ADR-0004、CONTEXT.md:99,141），不会触发这个问题。
- 用户在 Finder 里给媒体剪藏改了文件名，它和元数据侧档的对应关系会丢，可以接受。
- 如果 Workbench 以后修改 DiscoveryExclusion 里对点开头路径的处理，本决策要重新评估。
- 本方案还依赖 Workbench 的 md 预览能渲染相对路径的本地图片。代码层面已确认可以：`DocumentResourceHandler` 以 md 所在目录为根，提供该目录子树下的文件，不过滤点开头的路径（31.1 `app/Sources/FileboardApp/Inspector/DocumentPreview.swift:88-95`）。2026-10-06 M0 已在安装版 Workbench 1.3.1 空格预览中确认 `.assets/test/1.jpg` 显示成功，见 [实测报告与截图](../research/ALAG-1-results.md#5-workbench-本地图片预览通过)。

## 补记（2026-10-08，ALAG-8）

Windows 上这两个目录不隐藏：资源管理器不把点开头的名字当隐藏，而 File System Access API 设不了 Windows 的“隐藏”属性。用户定为接受，不做处理。剪藏文件本身的引用和显示不受影响。
