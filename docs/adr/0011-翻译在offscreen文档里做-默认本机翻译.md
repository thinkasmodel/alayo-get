# ADR-0011：翻译在 offscreen 文档里做，默认用浏览器本机翻译

- **状态**：已采纳（以 ALAG-24 实测通过为前提）
- **日期**：2026-10-17（ALAG-22，用户决定）

## 决策

- **翻译引擎**：第一期只用 Chrome 内置的 Translator / LanguageDetector API（本机翻译）。翻译层做成可替换的翻译引擎接口。第二期再加用户自填 key 的云端引擎（OpenAI 兼容接口、DeepL），只在用户主动开启时使用（ALAG-29）。
- **运行位置**：翻译在 **offscreen 文档**里运行。service worker 通过消息调用它。阅读器页面可以直接调用同一个翻译层。这一条取代 ADR-0001 里「本轮不启用 offscreen」。
- **保存时翻译**：先照常把原文剪藏写好，再在后台翻译，然后把同一个文件改写成对照译文。frontmatter 记目标语言和翻译状态。翻译失败或中断不影响原文。

## 理由

- Translator API 只开放给窗口环境，Web Worker 不能用（官方文档原文 "isn't available in Web Workers"），service worker 也就用不了。
- 放在工具栏面板里跑，面板一关翻译就断。放在注入网页的脚本里跑，会受网页权限策略的限制，离开页面也会断。offscreen 文档能在后台活过这两种情况。
- 用本机翻译，现有的隐私承诺（不上传内容，只联系被保存的网站）和商店的数据使用声明都不用改。云端引擎由用户自己开启，开启时提示文字会发给哪个服务。
- 先写原文再翻译：本机翻译逐段排队执行，长文需要较长时间。先写原文不拖慢保存，翻译失败也不丢内容。

## 考虑过的方案

- **云端翻译为默认**：质量和语言覆盖更好，但违背已发布的隐私承诺，商店也要重新提审。
- **翻完再写文件**：文件只写一次，但保存要等完整个翻译，失败时连原文都可能没存下。

## 后果

- 多维护一个 offscreen 文档和一套消息往返（ADR-0004 当时就是为了避免这个才不启用 offscreen）。
- 只支持桌面版 Chrome，移动端没有这个 API。语言对以 ALAG-24 的实测为准。实测不通过就回头重议本 ADR。
- 首次使用某个语言对时要下载模型，需要联网。隐私页的措辞以实测观察为准。
- 后台改写剪藏文件时可能和面板写回批注撞车。改写前要核对文件，两边只传修改意图，不传整份内容（项目 lessons 2026-10-09）。
